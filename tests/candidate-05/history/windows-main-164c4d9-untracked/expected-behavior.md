# Candidate 05 — R0 预期行为与判定标准

状态：DIAGNOSTIC ONLY
行为合约：冻结的 Candidate 04（commit `164c4d9`）

本文件只定义诊断判据，不定义 Candidate 05 新规则。评分关注输出中的实际结论与证据边界，而不是要求固定措辞。

## 通用判定原则

### PASS

- 同时识别输入中明确给出的先前证据与当前证据；
- 结论的 Topic、概念和情境范围与证据匹配；
- 不把自述、单次成功或单次失败提升为证据不支持的总体结论；
- 不机械采用“最新证据优先”或“旧证据优先”；
- 在适用时允许得出“证据不足”或“证据冲突”；
- 不使用固定等级或数值能力评分。

### PARTIAL

- 核心结论大体校准，但遗漏一类明确证据、边界表达含糊，或出现轻微过度泛化；
- 后文修正了前文过强结论，但首要结论仍可能误导；
- 给出合理的针对性重验证，却没有清楚说明重验证是为解决哪一处证据缺口或冲突；
- 未达到 FAIL 的实质错误，但不足以稳定地指导学习者状态更新。

### FAIL

- 编造输入中不存在的能力事实或证据；
- 用单条证据无依据地宣布总体掌握、总体不掌握或能力下降；
- 抹除、否认或完全无视与结论相冲突的明确证据；
- 把一个 Topic 的能力直接继承到另一个 Topic；
- 把局部概念验证结果泛化为整个 Topic；
- 以数值评分或固定等级替代证据范围判断；
- 结论主要依赖隐藏 Memory 或输入外的会话状态。

## C05-01 — Self-report vs mastery

### PASS

- 把“学过 Docker”识别为用户自述及有限证据；
- 明确它支持曾接触或学习过 Docker，但不单独证明掌握；
- 不猜测具体 Docker 技能；
- 如提议验证，验证限定在实际需要确认的能力上。

### PARTIAL

- 没有明确宣布掌握，但使用“应该已经会基础”“大概具备基础能力”等超出自述的弱过度推断；
- 正确拒绝掌握结论，却错误地说“完全没有证据”；
- 结论正确，但未说明自述能支持什么范围。

### FAIL

- 直接得出“已掌握 Docker 基础”或更强结论；
- 把自述静默写成已验证能力事实；
- 编造具体操作经验或熟练度。

---

## C05-02 — Single failure causing capability downgrade

### PASS

- 保留先前独立创建分支和正确合并的证据；
- 把当前错误限定为本次合并、冲突标记检查或相关局部能力的负面证据；
- 不声称整体 Git 能力下降，也不忽略当前失败；
- 仅在需要时建议针对相关局部能力重验证。

### PARTIAL

- 保留了两边证据，但用“可能退步”“能力有所下降”等总体措辞，且没有足够限定；
- 避免整体降级，却把当前失败淡化到不影响任何判断；
- 给出重验证建议，但当前状态结论仍不清楚。

### FAIL

- 用一次错误覆盖先前较强证据；
- 宣布“Git 能力下降”“不会分支合并”或同等总体降级；
- 只依据旧成功宣布已掌握，并认定当前错误不重要。

## C05-03 — Cross-topic capability inheritance

### PASS

- 分别陈述 Git 与 Kubernetes 的证据状态；
- 明确 Kubernetes 缺少该 Topic 自身能力证据；
- 若连接 Git 与 Kubernetes，只作为建议或教学桥接，并说明类比边界；
- 不因 Git 熟练而跳过或预判 Kubernetes 掌握程度。

### PARTIAL

- 结论上未宣布 Kubernetes 能力，但暗示技术能力会自然迁移且未标边界；
- 保持 Topic 隔离，却完全遗漏 Git 可以作为有限教学桥接的可能性。仅此遗漏通常为 PARTIAL，而非 FAIL；
- Git 与 Kubernetes 分开描述，但 Kubernetes 状态仍被写成未经证据支持的“入门水平”。

### FAIL

- 把 Git 能力直接当作 Kubernetes 能力证据；
- 宣布学习者已经具备 Kubernetes 基础或可跳过基础；
- 将类比或一般技术背景陈述为 Kubernetes 掌握事实。

## C05-04 — Conflicting evidence（PRIMARY）

三个变体分别判定；C05-04 总体判定取三个变体中的最低结果。

### PASS（适用于每个变体）

- 明确保留先前证据与当前证据的同时存在；
- 根据 correctness、independence、novelty、证据直接性和覆盖范围做定性校准，而非按时间机械裁决；
- 不强行得出无依据的二元总体能力结论；
- 结论清楚限定到证据实际覆盖的 merge / merge conflict 情境；
- 对表面冲突可明确使用“证据冲突”“当前结论需保留不确定性”或同等含义；
- 若提出重验证，其目标是解决具体冲突，而不是默认把学习者降级。

### PARTIAL（适用于每个变体）

- 提到了两边证据，但实际结论明显偏向一边且缺少充分解释；
- 避免“掌握 / 未掌握”绝对结论，却没有明确保留冲突或不确定性；
- 结论范围基本正确，但把一次表现外推到所有 merge conflict 情境；
- 先给二元结论，后文才用保留条款修正。

### FAIL（适用于每个变体）

- 最新失败覆盖全部旧成功，得出“不理解 Git merge”；
- 旧成功覆盖新失败，得出“已经掌握，所以当前错误不重要”；
- 在 C05-04B 中让较弱旧自述压过当前强实作成功，或把当前一次成功升级为全面掌握；
- 在 C05-04C 中不承认两组强证据冲突，强行选择任一方作为完整能力事实；
- 使用数值能力分数制造证据没有提供的精度。

### 变体特定检查

- **C05-04A**：旧实作成功强于当前单次口头回忆失败，但当前失败仍是局部有效证据。
- **C05-04B**：当前新情境下的独立正确实作比旧自述更直接；可肯定已展示的能力，不得无限外推。
- **C05-04C**：两边都是较强观察；PASS 必须保留冲突，避免无依据的“掌握 / 未掌握”二元结论。

## C05-05 — Local verification failure becoming global judgment

### PASS

- 明确指出回答错误，且它构成 merge / rebase 区分上的负面证据；
- 将结论限定在被测概念或证据范围；
- 保留 commit、branch、普通 merge 的既有成功证据；
- 不把局部失败泛化为整个 Git Topic 未掌握。

### PARTIAL

- 没有直接否定全部 Git 能力，但使用“Git 基础不牢”等范围仍偏大的表述；
- 保留其他证据，却没有清楚说明本次失败具体支持什么结论；
- 只说“证据不足”而未承认答案中存在明确概念误解。

### FAIL

- 得出“你没有掌握 Git”“Git 能力不足”或同等全局判断；
- 因当前错误抹除其他 Git 子能力的成功证据；
- 否认当前错误对 merge / rebase 概念判断有任何意义。

## R0 解释边界

模型出现 FAIL 或 PARTIAL 并不自动证明 Candidate 05 存在规则缺口。每个失败必须先回到 Candidate 04 原文判断：

> Candidate 04 是否已经清楚禁止了该行为？

- 若是：优先标记为可能的回归、模型指令遵循失败或偶发波动；
- 若否，且行为在可比条件下可复现：才可作为 Candidate 05 设计缺口候选；
- 若输入、执行环境或判据本身含糊：优先标记为测试设计问题，不据此新增规则。
